# 已验证节点复用与目标账号独立采集方案

日期：2026-09-19。设计基线：插件 0.5.1、当前仓库的 Sub2API 0.2.7 扩展接口。

**实施状态：首版已于 2026-09-20 完成，最终交付版本 0.6.1。** 实现位于独立仓库 `D:/Demo/s2plugin/plugins/ccodex-sleep-state`，见[最终验收与审计修复报告](D:/Demo/s2plugin/plugins/ccodex-sleep-state/docs/reports/2026-09-20_account-route-reuse-0.6.1-release.md)和[当前方案记录](D:/Demo/s2plugin/plugins/ccodex-sleep-state/docs/plans/2026-09-19_ccodex-sleep-state-account-route-reuse-plan.md)。下文保留设计时的 0.5.1 基线；第 9 节增强仍按原方案留待后续，不属于本次首版范围。

## 1. 目标与交付范围

账号 A 已在节点 R 上取得符合规则的 `X-Codex-Turn-State`。用户希望让账号 B 尝试相同节点，使用 B 自己的凭据独立采集，并在成功后只为 B 的目标模型配置该出口。

复用的是节点身份和连接配置。A 的成功结果提供候选依据，不证明 B 也能成功；A 的鉴权、工作区、state、个人/Team 规则均不复制给 B。state 长度合格只是本地规则判断，不代表模型质量、账号权限或额度保证。

首版完整交付包含：从 A 的合格结果发起 B 验证、按 B 规则显示结果、验证通过后应用到 B 的选定模型、恢复继承设置、账号间状态隔离，以及双账号真实签名包验收。保持原发布者签名与单包导入，版本号在实施发布时确定，本方案不预先宣布成品。

### 1.1 两种实现方式的选择

| 方式 | 工作方式 | 额度与生效边界 | 本方案安排 |
| --- | --- | --- | --- |
| 验证后配置出口 | B 先做一次单节点诊断；确认后保存 B 的路由绑定；下一次实际请求按 B 当前策略重新采集 | 通常需要一次验证请求，以及之后一次或多次有界采集；第二次采集仍可能失败 | 首版正式范围，兼容现有宿主，明确展示额外采集成本 |
| 验证并直接启用 B 的候选 state | 只暂存在内存中的 B 候选令牌，配置提交确认后，在相同 B 会话和路由代际中启用 | 可避免立即重复采集；需要候选租约、有效期重验和可靠的提交确认 | 独立后续增强，不能偷偷改变现有纯诊断语义；见第 9 节 |

首版允许管理员明确选择“同时为 B 的当前模型启用采集与注入”；默认保留 B 的原策略。该选择必须展示它会产生后续模型请求及额度消耗。严禁自动关闭 B 的失败关闭策略、重置 401/403/429 暂停，或修改宿主账号选择逻辑。

### 1.2 不在本次范围内

- 把 A 的 state 注入 B，或让多个账号共用一份 state 缓存。
- 将完整 state、Authorization、Cookie、凭据摘要写入普通配置、验证历史或浏览器。
- 为了验证读取 Codex 登录文件、宿主数据库中的凭据，或在插件页要求用户粘贴令牌。
- 自动轮询所有账号、无限更换节点、绕过上游暂停、自动重放正式生成。
- 以节点 ID 推断独立公网 IP；识别真实出口 IP 如需增加，应单独设计目标与隐私边界。

## 3. 用户操作流程

### 3.1 从 A 的结果选择节点

在 A 的逐节点验证表中，给 `qualified=true` 的结果增加「用其他账号验证」按钮。显示 A 的账号 ID、模型、节点名称、验证时间和采用的规则。历史结果可以提示节点曾经成功，但只有当前进程可核实的结果才能发起本功能；历史记录本身不带验证授权。

点击后打开设置面板，明确展示“候选节点 R 来自 A 的验证结果”。节点以稳定 ID 绑定，不能靠名称、列表位置或完整代理 URL 在 UI 中复制。

### 3.2 选择 B 的运行会话

目标列表只列出当前插件已有的 OpenAI OAuth 运行会话，按账号 ID 与模型显示。相同账号有多个工作区/凭据会话时显示不同的临时会话标识，避免用户误选；不能显示鉴权值或可持久关联的凭据摘要。

本入口要求 A 与 B 的宿主账号不同。默认推荐相同模型，但允许用户明确选择 B 的其他已建立模型会话，按 B 的实际模型和规则测试。套餐规则不从 A 复制。

B 没有会话时提示“先让一次 B 的请求经过插件，再刷新”。成功到达上游不是建立会话的唯一条件；只要插件正常取得该次鉴权并借用会话即可。若宿主没有选到 B，插件不能假装创建 B 会话，也不能私自控制宿主调度。需要时由用户通过现有宿主账号绑定/测试范围让请求命中 B。

### 3.3 用 B 验证 R

面板显示“仅使用 B 的凭据验证 1 个节点，会消耗 B 的额度”。点击后异步执行，保留现有每轮上限、冷却、进程全局采集槽和取消行为。处于普通冷却可以排队等待；401/403/429 上游暂停未解除时不发请求。

开始前必须确认 R 仍在 B 可使用的路由集合中，连接参数代际与来源候选一致，并且没有被人工全局停用。若 B 使用独立代理源且没有 R，返回“目标账号来源不包含该节点”；首版不自动把 A 的来源或代理密码写入 B。用户可先通过现有来源设置调整，再重新验证。

任务只提交节点 ID 和 B 会话引用。实际 HTTP Authorization、ChatGPT-Account-Id、模型和账号规则全部从 B 的运行会话取得。

### 3.4 展示对照结果

| 节点 | A 的已观察结果 | B 的本次结果 | 后续操作 |
| --- | --- | --- | --- |
| R | 曾取得合格状态头 | 合格，显示 B 实测/目标长度 | 可以「仅应用到 B 的此模型」 |
| R | 曾取得合格状态头 | 有头且可解析，但规则不符 | 保留 B 配置，显示形状差异 |
| R | 曾取得合格状态头 | 缺头、回复不完整或网络失败 | 保留 B 配置，允许在规则允许时重试 |
| R | 曾取得合格状态头 | 登录、访问或限流暂停 | 停止验证，展示等待/处理原因 |

“B 验证合格”只描述这次短请求。不能因此显示“B 已修复”“B 已启用 state”或“B 正式请求成功”。

### 3.5 应用与恢复

应用前展示将修改的账号 B、目标模型、原路由、新路由及策略开关。默认范围仅为 B 的当前模型。首版不提供“一次应用到 B 全部模型”，避免将未验证范围误写为通过。

用户确认后持久化模型级路由覆盖；保留其他账号、其他模型、失败关闭策略和上游暂停。如果用户明确勾选“为此模型启用采集与注入”，在同一配置差异中加入这三项精确范围的开关；否则仅设置路由。

保存成功显示“B 的该模型出口已配置；本次验证没有缓存 state”。若采集与注入开启，下一次 B 请求按原预算重新采集；若没有开启，显示普通转发状态，并提供明确的开启入口。

提供「恢复继承设置」删除这一条模型覆盖；提供「恢复上一次设置」恢复本次保存前的同一条绑定。恢复操作同样使用 revision/CAS，不覆盖用户随后作出的修改。恢复的是配置，不恢复已过期、已淘汰的内存 state。

## 4. 数据设计与隔离

以下均为拟议数据模型，不是现有 0.5.1 已支持的字段。

| 对象 | 主键或作用域 | 可保存的内容 | 禁止混入 |
| --- | --- | --- | --- |
| 节点目录 | 稳定 `route_id` 与连接参数代际 | 名称、协议、来源身份与 transport 引用；来源秘密仍由原有宿主管理 | state、账号鉴权 |
| 目标验证任务 | 随机 `job_id`，来源结果引用、目标会话、节点代际 | 执行状态、规则版本、模型、结果时间、原始头存在性/长度/块数 | 完整头、Cookie、Authorization |
| 生效检查凭据 | 服务端内存内的短期结果引用 | B 的会话代际、规则摘要、节点代际、目标模型和过期时间 | 前端可自行构造的“qualified=true”授权 |
| 账号模型绑定 | 宿主账号 ID + 精确出站模型名 | `route_id`、路由模式、可选的显式模型策略覆盖、来源验证审计 ID | A 的身份或 state、B 的完整 state |
| 资格历史 | 账号/模型/节点及不可逆向使用的记录 ID | 脱敏结果、时间、规则和失败类别；历史只用于显示 | 可跨重启充当有效授权的旧会话引用 |
| 活动 state | 账号 + 凭据代际 + 工作区 + 模型 + 路由代际 | 该会话自己采集的 state，仅内存 | 从 A 拷贝到 B 的令牌 |

结果有效窗口拟定为 **5 分钟**，并额外要求会话、凭据代际、工作区、规则和节点连接参数均未变化；时间窗口不是 state 的真实服务端有效期。A 的旧结果失效只取消其候选依据，不改变已经完成的独立 B 检查。B 的验证过期则必须重新验证，不能只改时间戳。

可选持久化历史只写无凭据元数据，按保留数量和时间清理。首版绑定配置通过宿主加密配置保存，完整 state 不存库。B 的实际 state 缓存可以继续沿用现有内存状态机。

### 4.1 模型级覆盖与缓存键

在 `AccountOverride` 下增加 `model_route_bindings`，以模型名为键。有效配置优先级为：全局配置 → 账号覆盖 → 该模型的显式路由/策略覆盖。没有该字段的旧配置行为不变，不给旧账号自动增加固定路由。

绑定 R 后，采集固定在 R，正式请求采用同一节点；不能让已有独立随机/固定出口在更高层再次覆盖该绑定。要在变更预览中明示这种优先级。B 的其他模型继续使用原规则。

拆分“节点集合签名”和“路由选择策略签名”：账号 B 选择 R 不应重建 A 的节点集合；同一节点集合可以共享不可变 transport，但 state 与采集会话始终独立。缓存应包含目标、有效模型配置和源集合代际；停止使用“同账号新引擎一律淘汰其他引擎”的规则，以免 B 的两个模型请求相互清空状态。

只退役配置确实改变的 B/模型实例，立即取消它的后台任务，等待在途请求排空后释放资源。A 的 state、active/ready、冷却、验证任务和连接不变。共享的凭据暂停记录继续有效，配置切换不能重置上游拒绝。

### 4.2 节点池拆分与迁移

将现有节点生命周期至少拆成三个维度：

1. **全局管理状态**：管理员明确停用 R 时，所有账号都必须尊重。
2. **传输诊断**：带时间的连接错误/超时记录，不包含 state 是否合格；恢复使用须按连接测试或现有重试策略处理。
3. **使用与资格记录**：按账号/模型/节点隔离。A 已用、A 形状不符不能耗尽 B 的候选，也不能把 B 的拒绝变成所有账号的代理失败。

迁移现有只有 route ID 的 `used` 记录时，归入无账号归属的历史，不能猜测属于 A 或 B；保留人工 disabled 和可确认的传输失败。保留 0.5.1 对错误资格失败的定向修复。迁移使用文件锁、schema 版本、可恢复备份和幂等标记；失败时明确提示，禁止整体清空。认领与完成仍使用修订标识，防止完成事件覆盖人工停用/回收或较新的领取。

## 5. 拟议接口与业务检查

保留 `config.load/config.save` 桥接和后台任务形式，不增加前端直接管理 API 访问或新的凭据权限。以下操作拟放在一次性 `core_request`；实现后必须从规范化配置移除，恢复/重启不能重放。

| 操作 | 输入 | 服务端行为 | 输出 |
| --- | --- | --- | --- |
| `verify_route_for_account` | 来源运行结果 ID、目标 session ID、route ID、随机客户端操作 ID | 核实 A 候选和 B 身份/节点成员关系，排队一项 B 验证，不改路由 | job ID、排队/冷却状态 |
| `status` | 无或 job ID | 只返回脱敏运行快照；不触发新采集 | A/B 对照、目标规则、任务状态及可否应用 |
| `apply_account_route` | job ID、目标绑定的预期 revision、是否显式开启该模型保护 | 从服务端 B 结果解析账号/模型/节点，验证新鲜性后生成最小配置变更；不接收原始 state | 规范化配置、精确变更范围与应用状态 |
| `cancel_verification` | job ID 或 session ID | 取消未完成网络请求，保留已完成元数据 | cancelled |
| `remove_account_route_binding` | B 账号 ID、模型、预期 revision | 删除指定模型绑定，恢复继承；保留其他配置 | 新配置 revision |

现有普通 `verify_nodes` 可继续使用。新跨账号入口不能直接信任浏览器传来的 `core_report`；报告内容被更改后，不得产生新的应用资格。job ID 只定位服务端结果，过期、重启、目标凭据变化或被另一个模型误用时返回明确失效原因。

运行失败应使用稳定分类，例如 `TARGET_SESSION_MISSING`、`TARGET_SESSION_CHANGED`、`TARGET_ROUTE_UNAVAILABLE`、`TARGET_RULE_CHANGED`、`VERIFICATION_EXPIRED`、`TARGET_NOT_QUALIFIED`、`UPSTREAM_PAUSED`、`CONFIG_CONFLICT`。消息可以解释处理方式，但不拼接原始上游头、凭据或代理 URL。

首版单次目标验证最多发 1 个短请求；取消/网络超时不自动重试。UI 重复提交相同操作 ID 应返回原任务，不能再扣一次额度。正式请求仍保持“不重放已派发生成”的边界。

## 6. 配置提交、回滚与在途请求

当前宿主 `SaveConfig` 的顺序为运行时 Validate/Apply → 加密 → 数据库 CAS → 成功返回；失败时尝试恢复已存配置。首版必须明确继承这个契约：保存过程中可能有请求短暂使用候选配置，不能承诺运行时切换与数据库落盘完全原子。

验证动作与应用动作分离。验证完成前不改 B 的路由；应用前检查 job、目标、节点代际、规则、revision 和人工停用。变更仅限指定 B/模型，页面的其他未保存草稿不会混入。

Apply 必须是可逆、幂等且不主动采集的操作。CAS 失败时恢复 B/模型原配置，A 完全不动；正在执行的请求继续使用开始时的不可变快照，不进行自动重放。恢复失败应让宿主进入明确的插件不可用状态，不返回“已应用”。数据库提交失败时也不能将 job 展示为持久应用成功。

job 不因一次 Validate 调用便不可逆地消耗，因为宿主可能回滚或用户重试。它保留到过期或最终成功响应，重复提交相同 job 和相同目标绑定幂等；试图改变绑定目标则拒绝。进程重启后 job 失效，但已成功保存的绑定可以恢复，后续只用 B 新请求携带的身份重新采集。

若产品要求“落库成功前绝不改变 B 的任何新请求”，必须给宿主增加准备/提交/中止或等价的可靠确认协议。这是额外宿主能力，不能在现有插件里伪装实现，也不能把浏览器发来的“保存成功”当作可靠提交证明。

## 7. 运行状态与界面文案

| 状态 | 含义 | 可用操作 |
| --- | --- | --- |
| 待选择目标 | 已选 A 的候选 R | 选择 B 的会话 |
| 等待 B 会话 | 没有当前运行身份 | 刷新；提示通过宿主让请求命中 B |
| 排队/冷却 | 已接受验证任务，尚未发出 | 取消、查看最早执行时间 |
| 验证中 | 正在用 B 向 R 发出短请求 | 取消、查看进度 |
| B 合格 | B 本次响应满足其自身规则 | 预览并应用，仅在结果仍有效时可用 |
| B 不合格/失败 | 缺头、形状/时间不符、网络或流失败 | 显示细项，保留原配置 |
| 上游暂停 | B 的认证、访问或限流约束 | 显示等待/处理说明，不继续换节点 |
| 出口已配置 | B/模型的绑定保存成功 | 查看作用范围、恢复；不能写“state 已启用” |
| B state 已就绪 | 后续 B 自己的采集产生有效缓存 | 显示剩余时间，不展示令牌 |
| B 正式响应成功 | 实际业务请求完成 | 与采集就绪分别统计 |

验证表并排展示 A 与 B 的模型、规则、检查时间和节点身份。B 的失败不能覆盖 A 的历史结果；A 的绿色标识不能让 B 自动变绿。UI 提供“此操作会额外消耗 B 的 1 次短请求；应用后采集按既有预算另计”的明确提示。

## 9. 后续：保留 B 本次候选，避免重复采集

独立增加明确命名的“验证并准备启用”操作，保留现有 `verify_nodes` 的纯诊断契约。候选只可能来自 B 的本次请求，并带 B 的凭据代际、工作区、模型、规则版本、上游目标、route 稳定 ID 与连接参数代际。

候选仅内存保存，有效租约不超过 5 分钟且不能超过令牌剩余有效时间；应用时重新检查全部绑定。候选过期、B 凭据变化、路由变化、人工停用、上游暂停或进程退出即失效。任何字段不匹配都不启用，不能转给另一个 B 会话“补救”。

配置准备与提交必须获得可信的宿主确认；应设计可恢复的 commit/abort 协议或等价服务端确认机制，再把候选发布到 B 的状态机。仅看到 ApplyConfig 回调不足以证明数据库已提交。提交失败或确认缺失时不发布，回收候选；正式请求不因这个过程自动重放。

该增强的验收需要额外证明：只发生一次 B 采集，提交后下一条 B 生成使用同一 B 候选；CAS 失败/重启/重复提交/回滚不会发布或复用错误候选。完成前，产品只能提供第 1.1 节首版流程并如实说明再次采集。

## 10. 验收矩阵与发布门槛

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同节点对 A 合格、B 形状不符 | B 显示自己的长度/规则，不能应用；A 状态不变 |
| 同节点 A/B 都合格，令牌不同 | B 正式请求只可能携带 B 自己后续采集的值，绝不出现 A 值 |
| A 个人、B Team，或模型不同 | 使用 B 自己规则，不能沿用 A 的期望块数 |
| B 未建立会话/宿主没选中 B | 不发假验证、不读取登录文件，显示建立会话方式 |
| B 账号内其他模型正在请求 | 应用 B 当前模型不取消其他模型采集或清空其 state |
| A 正在流式回复时应用 B | A 的 SSE 完整、无额外采集、无路由切换或令牌丢失 |
| A 已用 R、B 尚未使用 | B 能独立验证/采集；不能被 A 的 used 标记挡住 |
| R 人工停用/连接参数改变/来源移除 | 拒绝应用；不能自动回收、偷偷直连或按同名替换 |
| B 凭据/工作区变化或验证过期 | 旧结果不能授权应用，重新建立 B 验证 |
| B 401/403/429 或仍处于暂停 | 不重置限制、不换号或换出口继续撞；A 不被 B 的局部资格错误污染 |
| 浏览器伪造 qualified 或 job/账号/模型组合 | 服务端拒绝，原绑定不变 |
| 重复点击、请求重试、取消 | 不重复发短请求；取消后不自动应用 |
| 两个管理页面同时保存/数据库 CAS 失败 | 明确冲突，恢复受影响 B 配置，A 无变化 |
| 应用后重启 | 绑定仍在，旧任务与完整 state 不恢复；B 新请求用自身身份重新采集 |
| B 再次采集失败 | 按 B 原严格/兼容策略处理，无已发送生成重放，不误判为 A 或全局代理失败 |
| 多宿主实例 | 不声称共享 RAM 验证结果；任务与确认需落在拥有 B 会话的实例，否则明确不可用；持久绑定按宿主配置同步语义恢复 |

最终验收必须使用**最终签名包**运行：宿主真实安装 → A/B 两套合成凭据 → CONNECT 代理 → 本地 TLS 服务按凭据返回不同 state → 完整正式 SSE。逐条核对代理连接来源、Authorization、模型、state 注入与不重放。既有 [签名包协议测试](../backend/internal/service/ccodex_sleep_state_signed_proxy_test.go) 可扩展，不能只使用伪造 UI 成功数据。

浏览器验收覆盖入口、不同会话、规则差异、合格/不合格、过期、取消、保存冲突、恢复继承及窄屏布局。保留 0.5.1 的“错形状兼容转发成功、严格本地拒绝不轮换账号”回归，防止新增绑定再次破坏代理可用性。

只有上述首版工作项与验收通过，才生成沿用既有发布者的正式包、校验文件和实际验证报告。`dist` 只保留当前交付四件文件；旧包可恢复归档。报告区分受控合成账号测试与真实账号结果，不将前者写成真实账号已修复。真实 A/B 验证会消耗额度，应由明确选择的账号与操作触发。
