# 稳定内核升级流程

## 目标

桌面客户端只从 `core-stable` 安装通过自动兼容验证的内核。上游发布后由定时任务自动合并、测试、构建并发布；正常路径不需要人工操作。

## 通道与职责

| 通道 | 触发方式 | 写入目标 | 客户端可见 | 用途 |
| --- | --- | --- | --- | --- |
| 上游发现 | 每 5 分钟 | 无 | 否 | 比较 `core-stable` 清单与 Sub2API 最新 Release；一致时不启动构建 |
| 自动验证 | 每小时及手动补跑 | 临时工作树与 Actions artifact | 否 | 合并、前后端与桌面全量测试、构建二进制与清单 |
| 稳定 | 自动验证全部通过后 | `core-stable` Release | 是 | 直接发布通过身份、能力与哈希校验的内核 |

## 自动升级阶段

工作流：`.github/workflows/core-sync.yml`

1. 读取最新官方 Sub2API Release。
2. 读取 `core-stable` 清单；版本和上游提交均一致则成功结束，不重复构建。
3. 在临时工作树上执行非快进合并，不写 `main`。
4. 只允许已审核的确定性冲突策略：
   - `README.md` 保留成本控制台版本；
   - `backend/cmd/server/VERSION` 使用新上游版本；
   - 上游 `v0.1.177` 的 `backend/internal/service/account_test_service.go` 使用 `.github/resolve-core-merge.ps1` 做三方合并，仅在预期的 OpenAI compact 探测注释冲突和内容指纹完全匹配时收敛，保留成本限流逻辑与 remote compaction v2 代码。
5. 任意其他冲突，或已审核文件的内容形状发生变化，立即停止，创建或复用阻断 Issue，稳定通道保持不变。
6. 写入 `CORE_VERSION`、`UPSTREAM_SUB2API_COMMIT`，运行：
   - 后端全量 Go 测试；
   - Tauri/Rust 激活、身份校验和回滚测试；
   - 前端全量测试、桌面内核升级 UI 测试和 ESLint；
   - 前端生产构建；
   - sidecar `--version` 身份校验；
   - SHA-256 与稳定清单生成。
7. 发布前再次读取 `core-stable`，若已有更高版本则拒绝覆盖，避免并发降级。
8. 所有门禁通过后，在同一次任务中更新 `core-stable`；客户端下一次检查即可发现。正常路径无 PR、无批准、无人值守。

## 何时才需要人工

- 出现已审核规则之外的未知代码冲突，或 `account_test_service.go` 的三方合并指纹不匹配；
- 任一后端、前端、Rust、身份、能力或哈希测试失败；
- 上游发行标签移动、版本倒退或稳定通道出现并发发布。

这些情况会停止发布并创建阻断 Issue，现有 `core-stable` 和用户当前内核保持不变。机器可验证的正常升级不会要求维护者操作。

## 客户端激活与回滚

客户端继续使用已有的双槽机制：

1. 客户端启动约 1.8 秒后检查，随后每 5 分钟复查；也可手动“检查全部更新”。
2. 发现更新后自动下载到 `pending`，验证 manifest、能力、归档哈希和二进制身份。
3. 下载完成后用户可点“立即重启并启用最新内核”，或在下一次正常启动时切换；切换前保留当前 `active`。
4. 激活时先复制当前内核到 `previous`，再替换 `active`。
5. 新内核启动后必须通过健康检查；失败则恢复 `previous` 并上报 `core-update-rollback`。
6. 稳定通道故障时停止发布；客户端已有版本不会因远端任务失败而变化。
7. 兼容更新器拒绝远端 SemVer 降级，因此不要靠改写稳定清单强制全局回退：启动失败会自动恢复客户端 `previous`；已成功启动但出现业务退化时，可在客户端点“回滚内核”，再发布版本号更高的前向修复。

## 发布后观察

晋升后至少观察一个业务高峰窗口：

- 桌面启动成功率、自动回滚事件和核心启动耗时；
- `/health` 失败、数据库迁移错误和端口占用错误；
- 请求成功率、429/402、TTFT P95 与总耗时 P95；
- `usage_logs` 写入、成本快照、经济采样连续性；
- CPU、常驻内存与日志增长率。

任何一项显著退化都暂停自动任务并发布前向修复。自动构建失败或未知冲突本身不会影响当前稳定客户端。
