# 插件升级后无法解密配置：故障记录与 v0.3.4 修复复盘

记录日期：2026-09-19。状态：修复已合并并发布，公开产物验证通过。本文记录本次处置时的状态；时间标注为 UTC。

本次问题的根因是宿主没有持久保存插件配置的 AES 密钥。缺少显式配置时，重启会生成不同的密钥，使数据库中的旧密文无法解密；v0.3.3 又在部分失败路径自动清空旧密文，造成二次数据损失。v0.3.4 已修复密钥持久化，取消自动清空，并提供先备份、再明确确认替换的恢复入口。

**恢复边界：已分享的原始 `.s2plugin` 无需重新编译、签名或打包。旧密钥已经丢失时，保留密文不等于能够恢复明文；v0.3.3 已删除的配置也不能通过更新或回退自动重建。没有匹配备份的用户需要重新填写一次设置。**

## 用户现象与影响

- 用户反馈桌面版升级后插件无法正常启动，依赖插件的 Codex 连接受到影响；卸载重装曾被用作临时处理，但后续重启仍可能复发。
- 用户在 0.3.2 → 0.3.3 更新期间反复遇到“解密失败时会清空旧配置”的状态。
- 插件已被分享给其他用户，因此不能把重新开发、重新签名或重新分发插件作为宿主故障的必要修复条件。
- 受影响条件是旧宿主未配置固定的 `TOTP_ENCRYPTION_KEY`，并且已有使用临时密钥加密的配置。升级只是触发重启的一种方式，普通重启也可以触发。

本次确认的是配置持久化与插件运行受阻的问题，没有统计全部受影响用户数，也没有证据将所有插件导入错误或上游连接错误都归因于本问题。显式固定密钥的部署不能直接按“每次重启换钥”推断为同样受损。

## 根因与错误修复

### 根因：密文持久化，密钥没有持久化

`backend/internal/config/config.go` 在缺少显式配置时生成随机的 `cfg.Totp.EncryptionKey`。插件配置加密使用这个值；旧版 `backend/internal/repository/security_secret_bootstrap.go` 只完成 JWT 密钥持久化，没有保存对应的加密密钥。

第一次启动用密钥 A 加密配置，数据库保存密文。下一次启动生成密钥 B，用 B 读取 A 的密文，真实 AES 回归复现了 `decrypt: cipher: message authentication failed`。重新安装插件可能移除旧配置或重新产生可读配置，但没有解决下一次重启换钥的问题。

### v0.3.3 的错误处理扩大了损失

v0.3.3 在配置读取、测试以及保存时遇到解密失败的部分路径清空了旧密文。这把“目前无法解密、仍可保留等待匹配备份”的数据，变成了“已经删除”的数据。启动路径也没有因此实现可靠恢复，不能把出现空默认配置视为插件已经恢复正常。

此前围绕更新退出顺序和插件停用的修复属于另一个必要环节：等待内核及插件子进程退出，可以避免旧进程残留，但无法弥补密钥未持久化。两类问题必须分别验证。

## v0.3.4 实际修复

### 持久保存同一把加密密钥

在创建加密器之前，将 AES 密钥存入现有 `security_secrets` 表，键名为 `totp_encryption_key`。后续启动读取同一值；并发实例通过唯一键约束与写入后回读取得同一密钥。

显式配置的密钥首次持久化后继续复用。显式值与已存值冲突、或数据库中的密钥不合法时，启动报错并保留原值，不生成替代密钥，也不在错误中输出密钥内容。

### 保留不可读配置，恢复必须明确确认

配置读取、测试、启用和普通保存遇到无法解密的配置时，保留原密文并返回 `409 / PLUGIN_CONFIG_UNREADABLE`，附带用于确认当前快照的配置摘要。启动插件进程前先检查解密结果。

新增管理员二次验证保护的恢复接口 `POST /admin/plugins/:id/config/recover`。恢复要求插件已停用、没有启用中的绑定，并校验旧密文摘要及数据库快照。宿主使用已安装的原二进制，在无路由绑定的临时进程中验证新配置；验证成功后，才在同一事务中备份旧密文并保存新密文。任一步失败均不覆盖原配置，成功后仍需手动启用。

迁移 `243_plugin_config_recovery.sql` 增加 `sub2api_plugin_config_backups`，不自动裁剪备份。显式卸载插件会依照外键级联删除其备份，因此需要保留恢复证据时，应优先使用恢复入口并做好数据库备份，不要先卸载。

### 保持原分享包兼容

宿主继续接收旧插件页面使用的 `config.load`、`config.save` 消息，由宿主展示恢复提示和未勾选的确认框。没有修改插件协议、清单、签名或业务权限，也没有将本机私有插件打入公共安装包或开发包。

## 用户恢复操作

1. 使用现有桌面更新入口或 0.3.4 安装包升级。升级后插件停用一次，原包和可读配置保留；确认配置后重新启用。同版本普通重启保留启用状态。
2. 如果仍提示旧配置无法解密，先保留数据库备份。存在匹配的原密钥和数据库备份时优先恢复，避免混用不同数据库的密钥。
3. 无匹配备份时，停用插件，在原配置页重新填写设置，勾选宿主的“备份旧密文后替换”确认并保存，再启用。无需请求作者重新打包。
4. 0.3.3 已清空配置的用户需要重新填写一次。重新安装原包可以作为必要时的操作，但不能替代升级宿主，也无法找回已删除的设置。
5. 使用独立远程宿主的部署须更新实际宿主；只更新本地桌面外壳不会替远程服务器修复密钥。

## 防止再次发生

- 持久化的密文必须有同生命周期的密钥；备份必须包含完整数据库及 `security_secrets`，不能只备份插件目录或密文。
- 不在读取、测试、启动或普通保存失败时自动删除原数据；数据恢复必须是独立、明确确认、先备份且可验证失败回滚的操作。
- 插件发布验收必须覆盖跨启动解密、升级后启用、同版本重启、旧密钥缺失、保存失败和并发恢复，不能只测单次启动中的保存与读取。
- 已分发插件的兼容验收必须使用原始签名包；禁止用重新编译后的包代替历史包验证后宣称旧包兼容。
- 临时撤回发布只用于控制新增分发，不能宣称已经修复现有客户端。修复交付必须包含更高版本、现有更新公钥兼容和公开下载验证。
- 对本次未覆盖的真实上游推理及全部第三方插件，不做“所有场景都已验证”的承诺；后续问题继续保留原配置、版本和脱敏错误证据后定位。
