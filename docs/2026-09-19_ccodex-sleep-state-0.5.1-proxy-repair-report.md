# 0.5.1 代理转发故障与逐节点 state 验证

本次修复针对用户真实反馈：0.5.0 加入正常代理后 Codex 请求失败，界面只有连通性结果，无法判断每个节点实际返回的 `X-Codex-Turn-State`。

## 已确认的现场原因

现场实际安装的包为 `0.5.0-bef6184659e8-3817890019`，与上次交付哈希一致。对运行日志和无凭据节点池记录作只读检查，没有读取账号凭据或改写生产配置。

| 证据 | 观察 | 结论与修复 |
| --- | --- | --- |
| E-001：用户节点池记录 | 3 条记录均为 `failed / shape_mismatch`，每条尝试 1 次；更新时间为 UTC 2026-09-19 19:54:01、19:55:20、19:59:48 | 这些节点确实返回了可解析状态头，只是块数不符。资格失败不能等价为网络失败；新版恢复这些旧误分类，保留手动停用与真正网络错误 |
| E-002：用户宿主日志 | 洛杉矶 9 月 19 日 12:54–13:00，`gpt-6-astra` 出现 111 次上游 503／账号切换／选账号失败，最终客户端 502；多数耗时约 105 毫秒至几百毫秒 | 本地保护拒绝被当成上游故障。新版使用现有宿主支持的终止性保护错误，保留“正式请求尚未发送”事实，停止错误账号轮换 |
| E-003：插件停用时日志 | 中间停用时有 3 次 HTTP 200，约 8.8–9 秒 | 不能继续归因于普通代理或 Codex 自身断线，故障与插件开启相关 |
| E-004：真实旧签名包回归 | 合格头场景成功；错形状兼容场景返回 `503 pool_node_unavailable`；严格场景未返回终止性扩展错误；显式新模型返回 `400 unsupported_model` | 安装、握手和连通性测试不足以证明业务转发成功；新增同一签名成包链路回归锁定这些缺陷 |

旧包的错误路径 P-001：代理成功连接 → 返回可解析但不符合当前规则的状态头 → 0.5.0 将节点持久化标成 failed → 兼容转发也无法领取该节点 → 本地 503 进入宿主上游故障分支 → 切换账号后再次失败。严格模式还存在另一条路径：没有合格 state 的本地拒绝直接以普通 HTTP 503 返回宿主。

不能从历史记录还原当时完整头或精确长度，因为此前没有保存这类安全元数据；本报告不猜测当时实际是 292、312 或 332。

## 修复后的行为

- 收到头但形状、时间不符，以及缺头/非法头，都与代理连接失败分别处理。资格不合格不会让兼容模式失去正常代理。
- 严格模式仍按用户设置拒绝无合格 state 的请求，但使用 `PROTECTION_BUSY / RequestSent=false` 映射为宿主终止性扩展错误，不再进入上游 5xx 账号轮换。已发送后的本地失败仍明确 `RequestSent=true`。
- 首次同步采集整轮默认 20 秒，可设 1–60 秒，不再把最多 6 次 × 25 秒叠加到超过宿主期限。普通无 state 转发按配置轮询节点。
- 显式配置的模型白名单在请求检查和凭据会话建立两处统一生效，去掉独立上游应用写死的三模型限制。
- 未分类的 HTTP 403 改为凭据范围的有限暂停，遵守上游 Retry-After，不立即换出口跳过拒绝；401 认证阻断、429 限流约束保留。
- 升级时在文件锁内，只将旧版 failed 的资格误判记录恢复可用，不重置全部节点池、计数或手动停用状态。

## 每个节点的请求头验证

「测试连通性」只检查网络。「逐节点验证 X-Codex-Turn-State」使用运行会话中的凭据，向相同上游发送真实短请求，并按节点单独显示：

| 维度 | 显示内容 |
| --- | --- |
| 网络/HTTP | HTTP 状态、耗时、连接失败或未完成回复 |
| 状态头存在性 | 已收到或未返回头 |
| 封装解析 | 可解析或格式无效 |
| 实际形状 | 实际字符数、密文块数；不是按目标规则推测 |
| 当前资格 | 是否满足当前账号/模型规则，显示预期字符/块数与不合格原因 |
| 执行状态 | 待验证、正在验证、冷却、完成、上游暂停或取消 |

后台任务立即返回，不占用整份订阅的 UI 保存超时。每轮最多使用配置次数，轮间遵守采集冷却，继续剩余节点；401/403/429 或明确上游错误会停止并展示暂停原因。支持单节点、全部节点、取消和继续剩余。资格验证只生成诊断，不替换当前主用/备用 state，不改变固定路由，不把完整头写入配置或日志。

关闭注入和自动采集时，也可以明确发起这种验证。仍需要先有一次请求经过正在运行的插件，以获得该次请求的账号/模型会话；插件不会通过管理页面索取或读取用户的登录文件。该验证会消耗账号额度，页面明确提示最多涉及的节点数。

操作顺序：升级并启用宿主插件 → 配置正确代理 → 如需先恢复使用，点击「允许无 state 时正常转发」 → 发送一次匹配的 OAuth 请求 → 刷新运行状态 → 选择会话 → 验证全部或单个节点。严格模式如果确实没有合格 state，仍会明确拒绝；不能声称插件一定能从任意节点取得符合规则的值。

## 如何复现和验收

插件全量检查：在 `plugins/ccodex-sleep-state` 执行 `go test ./... -count=1`、`go vet ./...`；UI 契约执行 `python scripts/test-ui.py`。

新增 [真实签名包代理协议测试](../backend/internal/service/ccodex_sleep_state_signed_proxy_test.go)：

```text
真实包安装与签名校验
→ 宿主 RoundTripOpenAIOAuth
→ 已安装的真实 v2 插件子进程
→ HTTP CONNECT 代理
→ 本地 TLS 上游
→ 采集状态头及完整 response.completed
→ 正式请求注入与 SSE 回复
```

逐条校验 TLS 上游的连接来源确实属于代理发起的连接，防止仅采集走代理、正式请求绕过代理也被判成功。测试使用合成 Bearer、合成状态封装和临时测试 CA；只在 Linux 测试启动器中给已验签的原始二进制设置 CA 路径，不修改生产 TLS 行为或系统证书。

受控多节点测试还包含缺头、非法头、块数不符、合格、回复不完整和网络失败，以及冷却、取消、上游暂停、进程退出和敏感信息检查。它们证明实现行为；不等于已经用用户真实账号验证整份订阅。

本次未发起用户账号的付费生成，也未自动修改正在使用的生产插件设置。真实节点是否满足所选规则，以新验证表实际结果为准。节点数量不代表独立公网 IP 数量。

此前 0.5.0 报告所覆盖的安装、界面和局部适配测试不能替代这条成功转发验收；本报告更正该验证缺口。
